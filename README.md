# LOGIC FOUNDRY — 프로그래머블 공정자동화

Factorio 계열 공정자동화 게임. 단일 HTML 한 장, 의존성 0, 오프라인 실행
(`tests/offline_check.py` 가 그것을 검정한다 — 주장은 검사가 아니다).
**차별점은 제어기(Controller)** — 공장의 판단 로직을 플레이어가 노드 그래프로 직접 배선한다.

```
dist/Logic-Foundry.html   ← 더블클릭하면 바로 돈다
```

---

## 왜 다른가

기존 공정자동화 게임에서 "공장이 언제 무엇을 할지"는 개발자가 정해둔 규칙이다.
Factorio의 회로망은 곁가지이고, 대부분의 플레이는 배치 최적화다.

여기서는 그 판단 자체가 플레이어의 설계 대상이다.

- 제어기는 매 틱 노드 그래프를 **한 번 위상순으로 평가**한다.
- 되먹임(순환) 배선은 **직전 틱의 값**을 읽는다 — 실제 순차논리의 레지스터 한 단과 같다.
  그래서 SR 래치·카운터·샘플홀드·PID를 그대로 배선할 수 있고, 조합논리와 순차논리가
  같은 화면에서 섞인다.
- 정답 회로는 없다. 같은 목표를 히스테리시스로도, 타이머로도, 부하차단으로도 푼다.

대표적인 과제 세 개:

| 문제 | 제어기가 없으면 | 제어기로 |
|---|---|---|
| 철을 탄약과 연구팩에 어떻게 나눠 쓰나 | 손으로 켜고 끈다 | 재고 히스테리시스(SR 래치)로 자동 전환 |
| 발전기를 안 늘리고 정전을 막으려면 | 못 막는다 | 전력 만족도 < 95%면 저우선 라인부터 차단 |
| 적이 올 때 방어에 전력을 몰아주려면 | 못 한다 | 적 근접 센서 → 생산 라인 차단 → 터렛 사격허가 |

## 튜토리얼

처음 켜면 좌하단에 10단계 튜토리얼이 붙는다. **"다음" 버튼이 없다** — 각 단계는
세계 상태를 보는 `check()` 하나이고, 공장이 실제로 그렇게 됐을 때만 넘어간다.
눌러서 넘기는 튜토리얼은 손이 배운 게 없기 때문이다.

```
 1 채광기에 전기가 실제로 오는가        (net >= 0)
 2 채광기 출구 앞에 벨트가 있는가
 3 제련이 누적으로 일어났는가            (버퍼가 아니라 생산 카운터)
 4 상자에 철판이 5개 모였는가
 5 톱니가 만들어졌는가
 6 구리판을 만들었는가                   (여기부터 구리가 없으면 막힌다)
 7 연구가 실제로 진행됐는가              (researchProgress >= 1)
 8 제어기를 놓고 편집기를 열었는가
 9 제어기가 실제로 기계를 지배 중인가    (logicForced && fEnable)  ← 이 게임의 본체
10 터렛에 탄약이 들어갔는가
```

각 단계는 **한 줄에 하나씩** 지시하고, 드는 재료와 그 재료를 어디서 얻는지를 함께 적는다.
문단으로 쓰면 안 읽는다. 예를 들어 제어기 단계는 이렇게 편다:

```
1. 제어기   = 회로기판 5 + 철판 5
2. 회로기판 = 철판 1 + 구리선 3
3. 구리선   = 구리판 1 → 2개가 나온다
4. 셋 다 우측 [손 조립]에서 클릭으로 예약한다 (손도 시간이 걸린다)
5. 0 제어기를 놓고 좌클릭하면 노드 편집기가 열린다
```

건너뛰기는 한 단계만 넘기고, 닫아도 진행은 유지된다(건설 판의 [튜토리얼] 버튼으로 다시 연다).
저장/불러오기에도 진행이 실린다.

**재료가 모자라 배치가 막히면 그 자리에서 얻는 법을 알려준다** — "회로기판 5개 필요 (지금 0개)
— 1×철판 + 3×구리선 → 우측 [손 조립]에서 클릭". 부족하다고만 말하면 플레이어가 막힌다.

## 두 개의 저장소 — 보유 자재 ≠ 상자

- **보유 자재(STOCK)** = 플레이어가 들고 있는 것. **건물 비용과 손 조립은 여기서만 나간다.**
  손 조립은 **대기열**이다 — 클릭하면 재료가 즉시 빠지고 완성품은 레시피 시간 뒤에 나온다.
  한 번에 하나씩만 처리하므로 손은 언제나 "조립기 1대"가 한계다.
- **상자·기계 버퍼** = 세계에 놓인 물건. 인서터·벨트가 옮기는 것은 전부 이쪽이다.

둘은 자동으로 섞이지 않는다. 공장이 만든 것을 쓰려면 상자(또는 기계)를 좌클릭해
**[보유 자재로 가져오기]** 를 누른다. 아바타가 없는 게임이라 이 버튼이 "가서 꺼내오기"다.

> 이건 플레이 중 발견된 구멍이었다. 원래 회수 경로가 **철거밖에** 없어서, 시작 지급분을 다
> 쓰면 상자가 가득 차 있어도 아무것도 못 지었다. `inventory` 에 물건이 들어오는 경로를 전부
> 뽑아 보니 시작 지급·철거 환급·손 조립 결과·조립기 레시피 변경 반환 넷뿐이었다 —
> **생산물이 보유 자재로 오는 길이 없었다.**
> 회수는 옮기기지 만들기가 아니므로, 세계 총량이 변하지 않는지를 게이트로 못박았다
> (`stock.takeDoesNotDuplicate`).

**단축키는 건물에 고정돼 있다.** `1 벨트 · 2 인서터 · 3 채광기 · 4 용광로 · 5 조립기 ·
6 발전기 · 7 전주 · 8 상자 · 9 연구소 · 0 제어기`. 연구로 새 건물이 열려도 번호가 밀리지
않는다(예전엔 잠긴 것을 뺀 목록 순서로 매겨서, 물류학을 연구하는 순간 3=채광기가
3=인서터로 바뀌었다).

## 시각 언어 — 계기반

UI 는 창이 아니라 **장비의 앞면**이다. 어두운 세계 위에 밝은 아노다이즈 알루미늄 판이
얹혀 있고, 라벨은 판에 각인돼 있고, **수치는 판에 박힌 어두운 계기창(well) 안에서만** 산다.
게임 화면과 UI 가 같은 톤이면 서로 섞여 읽히므로 일부러 반대로 갔다.

| 역할 | 값 |
|---|---|
| 금속판 | `#d8d4cc` (하이라이트 `#eae7e0` / 그림자 `#c2bdb4` / 테두리 `#6d675e`) |
| 각인 글자 | `#1c2024` · 보조 `#585e65` · 라벨 `#63696e` |
| 계기창 | 바탕 `#23282c` · 글자 `#eae6dd` (안쪽 그림자로 파인 느낌) |
| 상태색 | 운전 `#1f6b46` · 주의 `#96610a` · 정지·위험 `#b23a10` · 구조 `#2c5470` |
| 위험 줄무늬 | `#e2b21c` — 게임 속 벨트와 같은 노랑, **경보 한 곳에만** |

글꼴은 웹폰트를 쓰지 않는다(단일 HTML 오프라인). 로컬 폰트 조합으로 성격을 만든다:
라틴·라벨은 **Bahnschrift**(DIN 계열, 각인체 느낌 — `wdth 75` 로 압축), 한글 본문은
**Noto Sans KR**, 수치는 **Consolas**(등폭·표 정렬). 글리프 단위 폴백이라 한 요소 안에서
라틴은 각인체로, 한글은 본문체로 자동으로 갈린다.

모서리 라운드는 0(금속판은 각지다), 버튼은 눌리면 실제로 들어가고, 장식은 없다.
힘은 **밝은 판 × 어두운 계기창** 대비 한 곳에만 쓴다.

## 조작

| 키 | 동작 |
|---|---|
| `WASD` / 방향키 | 이동 · `휠` 확대 · `우클릭 드래그` 화면 끌기 |
| `좌클릭` | 배치 / 선택 · **드래그하면 벨트가 방향까지 자동으로 이어진다** |
| `우클릭` | 철거 (자원 전액 환급) |
| `R` | 회전 · `Q` 커서 아래 건물 복제 |
| `1`~`0` | 건설 단축키 · `T` 연구 · `P` 오염 표시 · `H` 도움말 |
| `B` | 청사진 — 영역을 끌어 담고, `R` 로 돌리고, 좌클릭으로 붙여넣기 |
| `F2` / `F3` | 저장 / 불러오기 (창고 패널 버튼과 같다, 저장 칸 1개) |
| 제어기 **좌클릭** | 노드 편집기 |

편집기 안: 출력 포트에서 입력 포트로 끌어 배선, 입력 포트 클릭으로 해제,
배경 드래그로 이동, 휠로 확대. **예제 불러오기**를 누르면 재고 히스테리시스 회로가
대상까지 물린 채로 들어온다.

```bash
npm i -D playwright && npx playwright install chromium firefox webkit
```

나머지는 Playwright 러너(`tests/pwrun.js`)를 거치지만 **판정 로직은 harness.py 한 곳뿐이다** —
엔진마다 다른 채점기를 두면 어느 쪽이 맞는지 알 수 없게 된다.

#### 폰에 설치해서 쓰기

브라우저 탭으로 여는 것과 홈화면에 얹는 것은 다른 물건이다. 얹으면 주소창이 사라지고
아이콘이 생긴다. 그러자면 매니페스트·아이콘·상태바 메타가 필요한데, **배포본은 여전히
HTML 한 장이어야 한다** — 그래서 매니페스트는 `data:application/manifest+json` URI 로,
아이콘은 base64 PNG 로 문서 안에 넣는다(외부 참조는 여전히 0 · `offline_check.py` 가 확인).

아이콘 픽셀의 출처는 `tools/make_icon.py` 한 곳이다. base64 덩어리를 손으로 박아 두면
나중에 그게 어디서 나왔는지 알 수 없다. 생성기는 **자기 시험**을 갖고 있고(서명·IHDR·
네 색이 다 들어갔는가 + 깨뜨린 바이트열을 거르는 음성 대조군), 빌드가 그 시험을 먼저
돌린 뒤에만 아이콘을 박는다.

| 게이트 | 보는 것 |
|---|---|
| `mobile.manifestIsInstallable` | 매니페스트가 JSON 으로 읽히고 `standalone` · 아이콘 2종 |
| `mobile.appleTouchIconIsRealPng` | 링크의 base64 를 되풀어 PNG 서명과 192x192 확인 (iOS 는 매니페스트가 아니라 이 링크를 본다) |
| `mobile.standaloneMetaPresent` | 전체화면 메타 · 테마색 · `viewport-fit=cover` |
| `mobile.safeAreaPushesContentIn` | 노치 값을 44px 로 **덮어써서 계기가 실제로 내려오는지** 재고, 되돌리면 원위치인지까지 |

마지막 게이트가 이 절의 요점이다. `env(safe-area-inset-*)` 는 노치가 없으면 0 이라,
"규칙이 CSS 에 있는가"를 문자열로 훑으면 아무것도 검정하지 않는다. 값을 시험이 직접
덮어써서 **여백이 그만큼 밀려나는지**를 재야 한다.

여기서 두 번 헛디뎠고 둘 다 게이트가 짚었다. 안전영역 변수를 좁은 화면 미디어쿼리
**안에** 뒀더니 태블릿에서 통째로 안 먹었고(폰만 보고 GREEN 이라 했으면 아이패드
설치판이 깨진 채 나갔다), 그다음엔 상단 계기의 **박스** 위치를 재는 바람에 폰에서
"안 밀렸다"가 나왔다 — 좁은 레이아웃은 여백으로 미는 것이라 박스 top 은 0 그대로다.
지금은 눈에 보이는 계기(자식 요소)의 위치를 잰다.

**실제 기기 설치는 여전히 미검증이다.** 여기서 잰 것은 "설치에 필요한 재료가 문서 안에
있고 읽히는 형태인가" 까지다.

#### 완주 주행 — 마지막 한 건은 연구 **순서** 였다

`clear.js`(40분 자력 완주)는 이제 게이트 **14건 전부 통과**한다 — 연구 8/8 · 건물 22/22 ·
노드 35/35 · 심화 9/9 · 손실 0 · 최저 전력 96.0% · 열차 120타일 · 저장 175 KB.

오랫동안 이 게이트는 **연구 7/8** 로 RED 였다. 마지막 `automation-2` 가 76% 에서 시간이
끝났다. 자재를 늘리는 손잡이를 여섯 개 돌려 봤고 전부 실패했으며 그중 셋은 공장을 통째로
무너뜨렸다(아래에 그대로 남겨 둔다 — 실패 방식이 서로 달라 그 자체가 지도다).

답은 자재가 아니라 **순서** 였다. `belt-2`(고속 벨트)와 `automation-2`(생산 효율)는 값이
똑같이 적100+녹100 인데 효과가 다르다. 생산 효율은 기계를 1.5배로 돌려 **그 뒤의 연구팩
생산 자체를 앞당기고**, 고속 벨트는 라인이 짧은 이 판에서 거의 아무 일도 하지 않는다.
둘의 순서를 바꾸자 두 주행 모두 8/8 이 됐다 — 고친 것은 `TECH_ORDER` 한 줄이다.

**교훈**: 총량이 요구치를 넘겼는데도 못 끝내면, 남은 것은 "얼마나" 가 아니라 "언제" 다.
그리고 "언제" 를 바꾸는 가장 싼 손잡이는 **자기 자신을 앞당기는 항목을 먼저 드는 것** 이다.

##### 그런데 여유가 46초뿐이다 — 통과만 보면 안 보이던 것

8/8 을 확인한 뒤 **언제 끝났는지**를 함께 재는 게이트(`clear.techPaceHasMargin`)를 달았다.
처음 값은 **여유 13초**였다. 2400초를 달려 마지막 연구가 종료 13초 전에 끝난 것이다 —
GREEN 이지만 다음 변경 한 번이면 RED 로 돌아갈 자리였고, 통과/실패만 보던 동안에는
그게 보이지 않았다.

`automation-2` 를 `defense-ai` 앞으로 한 칸 더 당겨 **46초**가 됐다(방어는 손실 0 유지).
문턱은 주행 길이의 5%(120초)로 잡았다 — "공장이 5% 느려져도 다 끝낸다" 는 뜻이다.
**지금은 못 넘는다. 이 한 건이 유일한 RED 다.**

게이트가 함께 찍는 도착 시각 표가 다음 사람의 지도다:

```
logistics:779  military:354  steel:945   logic-mem:1089
logic-ctrl:1715  automation-2:1980  defense-ai:2073  belt-2:2355
```

첫 **779초 동안 값싼 연구 둘(각 적팩 20)** 밖에 못 끝낸다 — 병목은 후반 처리량이 아니라
**초반 램프**다. 녹색팩이 열리는 `logistics` 가 늦게 오고, 그 뒤 `logic-ctrl` 하나에
626초가 걸린다.

그래서 `logistics` 를 첫 자리로 당겨 봤다 → **붕괴**. 군수가 354s → 516s 로 밀리자 첫
습격(t≈570)에 전주·인서터가 뚫리고 전력망이 끊겨 회복하지 못했다(연구 2/8 · 손실 11).
**이 계획에서 `military` 첫 자리는 장식이 아니라 하중을 받는다.**

##### 램프 곡선을 재 보니 병목이 두 곳이었다

추측으로 손잡이를 돌린 시도가 일곱 번 실패했으므로, 이번엔 **계측기를 먼저 달았다** —
주행 스냅샷에 연구팩 누적 생산량을 넣어 램프 곡선을 뽑았다(누적은 `state()` 가 아니라
`tutorial()` 이 들고 있다. 처음에 `st.prod` 로 읽어 전 구간 0 을 얻었다).

```
t      적팩누적  녹팩누적   적팩/s  녹팩/s   조립기(도는 것)
 288       8       0     0.023   0.000    0(0)
 736      30       0     0.035   0.000    1(0)
 970      98       2     0.291   0.009    4(1)
1698     321      43     0.361   0.125   11(8)
2163     416     249     0.217   0.527   11(4)
2390     468     406     0.229   0.692   13(5)
```

- **초반 12분 동안 조립기가 0~1대다.** 계획이 군수 연구 앞에서 일부러 멈추고(첫 습격
  대비), 그 뒤 방어 설비를 먼저 세운 다음에야 팩 사슬로 간다. 적팩 30개를 736초에
  걸쳐 손 조립으로 만든다.
- **끝에서는 조립기 13대 중 5대만 돈다.** 자재가 아니라 **먹이는 속도**가 모자란다.
  요구치 도달은 적팩 t=2163 · 녹팩 t=2243 이고, 마지막 연구는 그 뒤 112초를 더 쓴다.
  종료 시점에 적팩 58개가 남는다(만들었지만 안 쓴 몫).

즉 남은 74초는 "조립기를 더 짓는다" 로는 안 나온다 — **초반 램프를 당기거나 후반
급유를 늘려야** 하고, 둘 다 이 팽팽한 계획을 다시 짜는 일이다. 그 값어치를 먼저
판단하는 편이 낫다.

##### 그때까지 실패한 여섯 가지 — 자재 쪽 손잡이는 전부 헛다리였다

처음엔 적팩이 65개 모자랐다(필요 410 · 생산 345). 조립기 진단(`asmDiag`)이 원인을
짚었다 — `sci-red:.:in50`, 적팩 조립기 셋이 구리만 50 을 쥐고 톱니 0 으로 멈춰 있었다.

공장 반경을 넓히고(`IN_R` 22 → 25) 톱니 조립기를 되먹임으로 늘리자 **적팩 438 · 녹팩
331 로 요구치(410 · 280)를 넘겼다.** 그런데도 연구는 7/8 이었다. 재고는 상시 0 이고 랩
2대가 들어오는 즉시 소비하므로, 그 시점에 남은 문제는 "얼마나 만드나" 가 아니라
**"언제 만드나"** 였다 — 그런데 그 뒤로도 자재 쪽 손잡이만 계속 돌렸다.

- **배분 정렬 뒤집기**(부족분 오름차순 → 내림차순): 공장 배분이 흔들려 배치 실패 2건 ·
  열차 정지. 연구는 그대로
- **톱니 재고 확보**(24개): 톱니는 터렛 재료(10개/기)라 방어가 무너졌다(손실 0 → **24**)
- **톱니 조립기 증설(초반)**: 시작 재고(회로 10 · 톱니 30 · 철판 60)로 **t=0 에 3대를
  지어** 부트스트랩이 사라졌다(건물 4/21 · 연구 0/8). 되먹임 문턱은 **시작 재고로는
  성립하지 않아야** 한다
- **톱니 조립기 증설(중반, 좁은 구역)**: 자리가 없어 계획의 녹팩 조립기가 밀렸다 —
  자재보다 **자리**가 먼저 막혔다. 구역을 넓힌 뒤에야 가능한 일이었다
- **탄약 줄이기**(후반 상한 110 → 70): 붕괴 — 손실 0 → **127**, 최저 전력 0%, 연구 7 → 4.
  격추 170 · 손실 0 이라는 여유는 탄약을 채워 둔 **결과**였지 남는 몫이 아니었다
- **계획 순서 당기기**(팩 사슬을 제련 확장 앞으로): 붕괴 — 앞당긴 조립기가 회로·톱니를
  먼저 가져가 **제어기가 한 대도 못 섰고**(노드 0/33) 손실 145 · 최저 전력 0% · 연구 6/8.
  이 계획은 한 줄을 당기면 그 아래가 굶는 **팽팽한 균형**이다

여섯 가지가 전부 실패했을 때 "계획 전체를 다시 설계해야 한다" 고 적었다. 그것도 틀렸다 —
여섯 개가 전부 **자재를 늘리는** 손잡이였고, 진짜 손잡이는 **연구 순서** 하나였다.
같은 방향으로 여섯 번 실패했으면 손잡이를 더 세게 돌릴 게 아니라 **다른 축**을 찾을 때다.

##### "구조적 구멍" 이라고 적었던 것은 순서 실수 두 개였다

직전까지 첫 습격(t≈450) 때 터렛이 1~2기뿐이라 발전기를 잃었고, 그것을 **습격 유예
300초와 군수 연구 완료 t≈400 사이의 구조적 구멍**이라고 이 문서에 적었다. 틀렸다.

군수는 적팩 20개면 되고, 적팩은 구리 1 + 톱니 1 이며, **시작 재고에 구리 30 · 톱니 30 이
이미 있다.** 즉 t≈150 에도 낼 수 있다. 드라이버가 늦었던 이유는 둘이었다.

- 적팩 제작이 `cuLine`(구리 용광로가 한 장이라도 구웠는가)을 기다리고 있었다. 그 가드는
  "구리를 다 써서 구리선 → 전주가 막히는" 교착을 막으려던 것인데, 전주 몫 12 만 남기면
  시작 재고로도 만들 수 있다 → 군수 완료 t≈400 → **t≈350**
- **안쪽 터렛 고리를 위협 순이 아니라 동·남·서·북 고정 순서로 지었다.** 바깥 고리는 둥지
  거리로 정렬하면서 안쪽만 고정이라, 터렛 3기 시점에 북쪽 자리가 비어 있었다 — 잃은
  발전기(74,61)와 전주(77,65)가 정확히 그 방향이고, 그 자리에 터렛이 있었으면 사거리 18
  안이라 닿았다. 안쪽도 같은 기준으로 정렬하자 **손실 3 → 0**

> **"구조적"이라고 부르기 전에 그 구조가 정말 막혀 있는지 계산해 본다.**
> 여기서는 시작 재고를 세어 보는 것만으로 아니었다.

##### 병목은 물류가 아니라 철이었다

생산 내역을 품목별로 떠 보니 40분 산출 철판 5847장 중 **톱니 2612(45%) · 탄약
1256(21%) · 회로 460** 이 나갔고, 녹색 연구팩의 병목은 **벨트 128개**였다. 벨트는 톱니를
거쳐 철에서 온다 — **연구가 막히는 이유는 결국 철이다.**

채광기+용광로 한 쌍은 철판 15장을 쓰고 20분에 370장을 돌려준다(채광 0.5광석/s,
제련 0.31판/s). 명백히 남는 장사인데 작업 줄에 묶여 늦게 섰다. `autoGen`·`autoCoal`
옆에 **`autoIron`** 을 두어 초반(`t<1200`)에 되먹임으로 최대 6쌍을 늘리자, 저장 탱크를
살 수 있게 되면서 **건물 21/21 · 노드 32/32** 로 커버리지가 닫혔다(게이트 10 → 11건 통과).

대가도 측정됐다. 기계가 늘면 오염이 늘고 오염은 습격을 앞당긴다 — 첫 습격이 세져
손실이 1 → 3 이 됐다. 그래서 증설을 "터렛 4기가 선 뒤"로 미뤄 봤더니 회수 기간(20분)이
모자라 **얻은 것을 전부 잃었다**: 연구 7→6종, 탱크 못 삼, 노드 32→29(게이트 9건 통과).
**철은 이르게 늘려야 값이 나오고, 초반 손실은 그 대가다.**

최저 전력 만족도 96.7%.

##### 방어는 계획이 아니라 되먹임이다

직전까지는 터렛이 작업 줄에 매달려 있었다. 그래서 5~9번째 터렛이 줄 차례를 기다리다
**피해가 난 뒤에** 섰다.

```
t=1063  터렛 4기 · 잃은 건물 1
t=1129  터렛 4기 · 잃은 건물 6 · 발전기 5→2대 · 전력 만족도 48%   ← powerHeld 실패
t=1197  터렛 8기 (이미 늦었다)
```

전력 게이트가 실패한 원인은 석탄도 발전기 수도 아니라 **발전기가 부서진 것**이었다.
`autoGen` 옆에 `autoTurret` 을 두어 진화도에 비례해(기본 6기 + 진화 6%당 1기) 미리
세우자 손실 10 → 1, 최저 전력 46.1% → 96.7%, 연구 6 → 7종이 됐다.

곁들여 두 가지가 걸렸다. 터렛(철판 20)을 사려면 **재고**가 있어야 하는데 이 공장은
철판 재고가 늘 0 이라(craft 와 feed 가 매 사이클 비운다) 목표가 10기여도 5기에서
멈춰 있었다 — 증기 발전소 때와 같은 문제라 같은 해법(`ironHold`)을 썼다. 그리고
터렛이 자재를 다 가져가자 제어기 2·4 가 안 서서 노드 커버리지가 32 → 29 로 후퇴했다.
**방어를 고치면서 커버리지를 깨면 고친 게 아니다** — 제어기 몫을 남기게 했다.

고리 기하는 건드리지 않았다. 남은 손실 1건을 없애려고 안쪽 고리를 8자리로 늘리고
(습격 26→47회·손실 3·커버리지 28) 바깥 반경을 20 으로 당겨 봤지만(커버리지 26·열차
정지) 둘 다 더 나빴다. 이 판의 좌표는 서로 맞물려 있어서 고리를 옮기면 공장 배치가
통째로 흔들린다. 원장에 적립했다.

#### 이 주행은 이제 재현된다 (2026-08-10 수정)

전에는 **코드를 한 글자도 안 바꾸고 6회 돌려 6회 다 달랐다.** 습격 손실 3~10, 최저 전력
46~94% 로 흔들려 `powerHeld` 가 주행마다 PASS 와 FAIL 을 오갔다 — 뒤집히는 게이트는
게이트가 아니다. 원인은 한 줄이었다.

```js
// newGame() 은 gameTime·accumulator·진화도·신호 버스·열차까지 되돌리면서
// 오염 확산 타이머 pollTimer 만 되돌리지 않았다.
```

페이지가 열리고 드라이버가 `reset` 을 부르기까지 게임은 실시간으로 잠깐 돈다. 그 시간은
머신 사정에 따라 다르고, 그동안 `pollTimer` 에 [0, 0.25) 의 잔여 위상이 남는다. 판을 새로
깔아도 그 위상이 살아남아 **확산·감쇠 스텝이 매 주행 다른 게임 시각에 떨어졌다.** 오염
0.1% 차이가 진화도 → 습격 규모로 증폭돼 40분 뒤의 손실과 전력 만족도를 갈랐다.

찾는 데 걸린 이유가 하나 더 있다. **결정론 지문(`G.stateHash`)이 오염 격자를 안 담고
있었다** — 누적 배출량만 담아서, 격자 총량이 갈리는 동안에도 지문은 끝까지 같은 값을 냈다.
지문이 못 보는 상태는 지문이 없는 것과 같다. 지금은 격자 총량과 진화도를 함께 담는다.

고친 뒤 40분 주행 2회가 게이트 13건과 지문 40개 전부 일치한다.

새 게이트 `tests/determinism.js` 가 이 부류를 막는다.

```
det.resetIsReproducible      같은 씨앗으로 reset 직후 지문이 같다
det.plainRunIsReproducible   같은 페이지에서 480초를 두 번 돌려 지문 8개가 같다
det.drivenRunIsReproducible  배치·재고 개입을 끼워도 같다
det.resetClearsPriorRun      **리셋 전에 7.3초를 돌려도 같은 결과** ← 이 결함을 잡는 검사
det.differentSeedDiffers     음성 대조군 — 씨앗을 바꾸면 반드시 갈려야 한다
```

마지막 줄이 없으면 앞의 넷은 "같다"가 아니라 "아무것도 안 본다"일 수 있다. 실제로 처음
만들었을 때 리그가 빈약해(엔티티 3개·채굴 0) 씨앗을 바꿔도 지문이 같았고, 그 음성
대조군이 그것을 잡아냈다. 되돌린 빌드에서 `det.resetClearsPriorRun` 이 FAIL 로 뒤집히는
것까지 확인했고, 돌연변이 시험에도 등록했다.

완주 주행에는 300초 브라우저 상한이 걸려 있었고 이 주행이 그 바로 아래에서 끝났다. 머신이
조금만 바쁘면 TIMEOUT 인데, 타임아웃은 "게이트가 잡았다"가 아니라 **판정 불성립**이라 조용한
검증 구멍이 된다. `LF_TIMEOUT` 으로 열어 뒀다: `LF_TIMEOUT=1200 python tests/harness.py clear.js`.

네 엔진에서 같은 장면(`tests/scene-factory.js`)을 찍어 눈으로 대조했다 — `shots/engine-*.png`.
차이는 한글 폰트 메트릭뿐이고 배치·색·아이콘·전선·UI 는 동일하다. Safari 자체는 Windows 에서
돌지 않으므로 **WebKit 엔진으로 대신했다** (실기 Safari 는 미검증).

### 게이트가 무엇을 보증하는가

판정은 화면 문자열이 아니라 `window.__GAME` 이 돌려주는 JSON 필드로만 한다.

- **처리량** — 벨트 15개/s, 인서터 0.833개/s, 채광 0.5개/s, 제련 3.2s/판을 SPEC에서 계산한
  기대값과 대조. 벨트는 "실렸는가"뿐 아니라 "10초에 18.75칸까지 갔고 그 너머는 비었는가"로
  앞뒤를 함께 조인다.
- **공개 숫자** — 위 처리량 게이트는 기대값을 SPEC에서 받아 쓰므로 **SPEC 자체가 바뀌면
  측정값과 오라클이 같이 움직여 아무것도 안 걸린다.** 실제로 채광을 0.5 → 0.25/s 로 절반
  깎고 돌렸더니 239건이 전부 통과했다. 그래서 문헌값 28개(Factorio 공개값 또는 이 게임의
  설계값)를 **시험 파일에 직접 적어** 두고 SPEC 원본과 대조한다. 같은 절에서 "증기 1개 =
  30 kJ" 항등식이 양쪽에서 성립하는지도 본다. 위 표의 숫자 중 SPEC 밖에 있는 것 —
  건물 소비전력(13·90·180·155 kW), 레시피 시간(3.2·16·0.5·5·6초), 적 체력(15/75/375) —
  도 같은 방식으로 못 박았다.
- **설명문** — 건물 설명문("0.5개/s 로 캔다", "600개 보관", "900 kW")은 플레이어에게 하는
  약속인데 상수와 떨어진 문자열이라 상수만 바뀌면 조용히 거짓말이 된다. 상수에서 문장에
  나와야 할 조각 22개를 만들어 실제 설명문이 그것을 담는지 본다. **문헌값 → 상수 → 설명문**
  세 단계가 이렇게 이어진다.
- **연구 효과** — 고속 벨트(15 → 30개/s)와 생산 효율(기계 1.5배 · 전력 0.8배)이 실제로
  그렇게 되는지 같은 리그를 연구 전후로 돌려 비교한다. 저장했다 열어도 유지되는지,
  새 판에서는 사라지는지까지 본다. 배수는 `TECH_EFFECTS` 표 하나에서 나온다 —
  예전엔 같은 숫자가 세 군데(연구 완료 · 저장 복원 · 시험 API)에 따로 적혀 있었다.
- **해금 목록** — 연구 화면의 "해금" 목록은 손으로 적은 문자열이고 실제 잠금은 건물·레시피·
  노드의 `tech` 표시가 한다. 양쪽을 둘 다 본다: 잠긴 것이 전부 목록에 있는가, 목록에 적힌
  것이 정말 그 연구 뒤에 있는가. **이 게이트를 켜자마자 20건이 빠져 있었다** — 강철 제련이
  유체 계통과 열차 계통 전체를 잠그는데 목록엔 "강철 레시피, 분배기" 두 줄뿐이었다.
- **튜토리얼 재료 문구** — 각 단계의 "필요" 줄("용광로 = 벽돌 5 + 철판 5")은 플레이어가
  그것을 보고 재료를 준비하는 문장이다. 비용표의 항목마다 이름 뒤 숫자를 문구에서 찾아
  22항목을 대조한다. 문구가 뒤처지면 따라 한 사람이 배치 버튼에서 막힌다.
- **도움말 본문** — 튜토리얼을 건너뛴 사람은 도움말(`H`)만 읽는다. 거기 적힌 숫자 약속
  ("전주 5×5", "8 타일/s", "5초가 지나면 간다", "0.5 이상이 참", "1틱 약 17ms")을 상수에서
  조각으로 만들어 본문에서 찾는다.
- **저장본이 어느 판에서 왔는가** — 저장본은 `v` 를 적어 왔는데 불러올 때 아무도 읽지
  않았다. 형식이 바뀌면 없는 필드가 조용히 기본값으로 채워져 "열었더니 연구가 사라졌다"
  처럼 나타난다. 이제 읽고, **거절 대신 알린다** — 거절하면 판 하나 올릴 때마다 남의
  저장본을 버리는 셈이다. 판이 없는 저장본도 "없음"으로 잡는다.
- **물질수지** — 땅에서 뽑은 개수 == 세계에 존재하는 개수 증가분 (벨트 위 재고 포함).
  복제·소멸이 생기면 즉시 어긋난다.
- **에너지수지** — 태운 연료 kJ == 실제 공급 kW × 시간.
- **오염 배출** — 배출/s == 20 × 발전기 부하 × 0.02. 부하를 알기 위해 소비자는 오염을 내지
  않는 인서터만 쓴다.
- **전력** — 공급<수요일 때 만족도가 공급/수요와 같고, **개별 기계에 그 값이 실제로 내려가
  생산속도가 그 비율로 느려지는지**까지 본다(집계만 보면 "표시는 맞는데 안 느려지는" 고장을
  놓친다).
- **제어 로직** — 히스테리시스가 중간대를 **아래에서 올라올 때는 켜진 채, 위에서 내려올 때는
  꺼진 채**로 지나는지(여기가 래치와 단순 비교기가 갈리는 유일한 지점), 되먹임이 정확히 1틱
  지연인지, 제어 노드를 지우면 지배가 풀려 플레이어 의사로 돌아오는지.
- **전투/교착** — 터렛 사살 시간이 15hp ÷ 50dps 와 맞는지, 건물 벽 뒤에 가둔 적 6마리가
  45초 뒤 전부 굳지 않았는지.
- **결정론** — 같은 시드 2회 상태해시 동일, **다른 시드는 달라야 함**(음성 대조군이 없으면
  "항상 같은 값"인 고장도 통과한다).
- **시각** — 프레임버퍼를 직접 읽어 빈 화면을 검출하고, 그 검출기가 실제로 작동하는지
  아무것도 안 그린 화면으로 확인한다. 건물 13종이 전부 빈 땅과 다르게, 그리고 서로 다르게
  그려지는지도 본다.

### 페이싱 — 기계로 잴 수 있는 밸런스

`tests/balance.py` 는 30분치를 헤드리스로 돌려 표로 뽑는다. **게이트가 아니다**(합격선이 없다).
모델링 가정은 "기계가 굶지 않는 완벽히 배선된 공장"이라 여기 나오는 오염·진화 속도는
**실제 플레이의 상한**이다. 출력 맨 위에 가정을 같이 찍는다.

| 시나리오 (30분) | 첫 습격 | 첫 손실 | 30분 진화도 | 누적 습격 |
|---|---|---|---|---|
| A 무방비 (채광5·용광로6·조립3·발전2) | 6분 | 6분 | 23% | 2파 |
| B 방어 (같은 공장 + 터렛 6) | 6분 | **없음** | 37% | 22파 / 110마리 |
| C 대형 (2배 규모 + 터렛 4) | 6분 | 6분 | 35%(20분) | 30파 / 150마리 |

읽는 법: **무방비 공장은 6분에 부서지기 시작하고, 터렛 6대면 110마리를 손실 0으로 막는다.**
크게 지을수록 오염이 늘어 습격이 빨라진다(C가 A보다 파도가 15배 많다). 초반 5분은 유예다 —
없으면 잘 지은 것이 벌이 된다.

보조 측정: 발전기 1대가 조립기 5대를 감당(155kW 기준 이론상 5.8대) · 시작 철광맥 1개 +
채광기 1대는 **151분에 4509개** 채굴 후 고갈(오라클 0.5개/s × 151분 = 4530, 오차 0.5%).

### 게이트 자체의 검정

`mutate.py` 는 소스를 한 곳씩 고의로 깨뜨리고 지목한 게이트가 실제로 뒤집히는지 본다.
바이트로 읽고 쓰고 대조하며(개행 변환에 속지 않기 위해), 문법 오류를 낸 돌연변이는
`INVALID` 로 분리한다(모든 게이트가 무너진 것을 "잡았다"로 오독하지 않기 위해).

이 역검정은 여러 번 **놓침(MISS)** 을 냈고, 그때마다 게이트가 실제로 고쳐졌다:
전력 게이트가 집계만 보고 개별 기계를 안 봤고, 히스테리시스 검정이 한 방향뿐이었고,
시각 총조사가 그림자만으로 통과했고, 테스트 훅 하나가 결함을 가리고 있었다.

## 자력 완주 주행에서 또 고친 것 — "말이 되는가"는 게이트가 안 묻는다

게이트 111건이 GREEN인 상태에서, **처음부터 끝까지 스스로 깨는 드라이버**(`tests/clear.js`)를
돌리며 전멸했다. 게이트는 전부 "이 기능이 명세대로 도느냐"를 물었지 "이게 말이 되느냐"를
묻지 않았다. 아래 7건은 전부 명세대로 돌고 있었다.

| 결함 | 뿌리 | 왜 안 걸렸나 |
|---|---|---|
| 터렛을 철거하면 **탄창이 10배**로 늘어남 | `e.ammo` 는 발 단위(탄창 1개 = 10발)인데 그 수를 탄창 개수로 환급 | 환급 경로에 게이트가 없었고, 테스트 훅 `remove` 는 환급 없이 지웠다 |
| 발전기를 철거하면 **넣어 둔 석탄이 소멸** | 석탄이 `e.inv` 가 아니라 `e.fuel`(에너지)에 녹아 있어 환급 루프가 못 봄 | 같은 뿌리(단위 불일치)의 반대 방향 |
| 터렛 14기가 15hp 적 하나에 **13발을 버림** | 같은 틱에 이미 죽은 적(hp≤0)을 뒤 터렛이 계속 조준 | dps 오라클은 터렛 1기로만 쟀다 |
| **손 조립이 즉시 완성** — 조립기(6.67초)보다 30배 빠름 | 시간 개념이 없었다 | "자동화할 이유가 사라진다"는 명세가 아니라 장르의 전제다 |
| 연구를 갈아타면 **먹인 연구팩이 증발** | `startResearch` 가 진행도를 무조건 0으로 | 49/50 에서 클릭 한 번에 98팩 손실. 되돌릴 방법 없음 |
| 튜토리얼이 "손 조립으로도 된다"고 안내하는데 그렇게 하면 **안 넘어감** | 판정이 보는 `prodStats` 를 손 조립이 안 건드림 | 안내문과 판정을 대조하는 검사가 없었다 |
| **강철이 아무 데도 안 쓰임** | 레시피·아이템은 있는데 소비처 0 | 적팩 50개짜리 연구가 "철판을 버리는 기능"을 열고 있었다 |

손 조립은 **대기열**로 바꿨다(재료는 즉시 차감, 완성은 레시피 시간 뒤, 한 번에 하나).
강철은 분배기의 재료가 됐고 분배기가 강철 연구로 옮겨 갔다 — belt-2·automation-2 의
선행이라 어차피 모두 지나는 길목이고, 분배기는 없어도 죽지 않는 편의 장비다.

### 독립 반증을 붙였더니 4건이 더 나왔다

다섯 갈래(광석 사슬·드라이버 물류·자재 오라클·결함 탐색·전투 오라클)로 따로 훑고,
주장마다 **반증 전담**을 붙였다. 주장 29건 중 24건이 반증돼 사라지고 5건이 남았다.
반증을 안 붙였으면 그럴듯한 24건을 고치느라 진짜 4건을 놓쳤을 것이다.

| 결함 | 뿌리 |
|---|---|
| 분배기 [출력우선]이 **남·서향에서 좌우 반대** | `cells[0]` 은 언제나 좌표가 작은 쪽인데, 이 집의 '왼쪽'은 진행방향 기준이다(레인 0 = dirCCW) |
| 철을 굽던 용광로가 **조용히 구리를 굽기 시작** | 비면 레시피가 풀리고, 다시 급광할 때 `ITEM_IDS` **선언 순서**가 정한다 — 플레이어가 볼 수 없는 순서다. 굽던 것을 기억해 먼저 시도하게 했다 |
| 편집기에서 **노드를 옮겨도 평가 순서가 안 바뀜** | 끌기 핸들러가 `graph.dirty` 를 안 세웠다. 이 파일에서 `dirty` 는 읽기 한 줄뿐이었다 |
| 도움말이 **"왼쪽 위부터 평가한다"고 거짓말** | 이어지지 않은 회로 사이의 순서는 DFS 구조가 정한다 |

마지막 것은 **코드를 고치려다 내가 위상순서를 깨뜨렸다** — 나무별로 뒤집었더니 두 나무가
공유하는 노드가 자기 입력보다 먼저 돌았다(`node.hold` RED). 원래 코드가 옳았고 어긋난 것은
문서였다. 그러면서 정작 중요한 계약 — **어떤 노드도 자기 입력보다 먼저 돌지 않는다** —
에 게이트가 없다는 것이 드러나 새로 달았다.

### 하네스 자신이 정직하지 않았다

`__GAME.place` 는 `free=true` 경로라 **비용·기술·광맥 검사를 전부 건너뛴다.** 계통 하나만
떼어 재는 시험에는 그게 맞지만, 그걸로 "자력 완주"를 주장하면 거짓이다 — 완주 드라이버가
**광맥 없는 땅에 채광기를 세워 놓고** 40분 동안 아무것도 안 캐는 것을 눈치채지 못했다.
플레이어와 같은 길인 `__GAME.build` 를 따로 만들고, 두 경로가 실제로 다른지를 게이트로
못박았다(재료 없으면 거절 · 광맥 아니면 거절 · 연구 전이면 거절 · 비용 차감).

### 게이트는 자기 버그를 잡는지까지 검정한다

새 게이트 20건에 전부 **음성 대조군**을 넣었다(아직 안 나왔어야 하는 시점, 없는 항목 취소,
병렬 처리 검출, 네 방향 전부 재기). `tests/mutate_new.py` 가 게이트마다 고친 줄을 원래
버그로 되돌려 **그 게이트가 실제로 뒤집히는지** 본다 — 15/15 가 잡는다.

두 번은 처음에 안 잡혔다. `turret.noOverkillWaste` 는 상한을 8발로 느슨하게 잡아
고치기 전 동작(터렛 8기가 각 1발)도 통과시켰고 — 정확한 오라클은 15hp÷5dmg = **3발**이다.
`furnace.remembersLastRecipe` 는 **철**로 시험했는데 철광석이 `ITEM_IDS` 첫 항목이라
고치기 전에도 철이 이겨서 구별이 안 됐다 — 구리로 바꾸니 잡힌다.
둘 다 같은 교훈이다: **통과하도록 만든 게이트는 통과한다.**

## 제어기를 문장으로도 쓴다 — 코딩을 안 해 본 사람을 위해

노드 편집기는 사실상 프로그래밍 언어다. 빈 캔버스에 노드 30종을 놓고 선을 잇는데,
**무엇을 만들지 이미 알아야 시작할 수 있다.** 노드 이름에 `선택 (조건 ? A : B)` 처럼
삼항연산자가 그대로 적혀 있었고, SR 래치·엣지 검출·샘플 홀드는 그 분야 말이다.

그래서 같은 것을 문장으로도 쓸 수 있게 했다. 제어기를 열면 **이쪽이 먼저** 나온다:

```
규칙 1  [재고충분]
  만약  상자 #14 의 [철판] 이 [200] 개 [보다 크면]
  그래서 [조립기 #15] 를 [끈다]
  기억  [한 번 참이면 유지하고, 따로 정한 조건에서만] · 되돌리는 건 [200] [보다 크면]
                                                   · 되돌리기는 [30] 초에 한 번만
  → 만약 상자 #14 의 철판이 200개 보다 크면 그래서 조립기 #15 을 끈다 · 지금 34개
```

은행 자동이체 신청서와 같은 물건이다 — 문장이 이미 다 쓰여 있고 빈칸만 고른다.
규칙이 없으면 대신 **하고 싶은 일 카드**가 나오고(재고·부하 차단·방어·경보·표시),
고르면 문장이 절반쯤 채워진 채로 열린다. 연구가 안 된 카드는 회색에 이유가 붙는다.

**문장은 두 번째 런타임이 아니다.** 노드와 배선을 대신 놓아 줄 뿐이고 평가는 여전히
`35_logic.js` 하나가 한다. 그래서 저장·튜토리얼 판정·전투가 전부 그대로 통하고,
[회로로 펼치기] 를 누르면 그 문장이 만든 **진짜 노드 그림**이 나온다. 배우는 사다리가
따로 필요 없다 — 쓰던 것이 그대로 그림이 된다.

읽기 16종 · 비교 6 · 계산 7(눅이기 포함) · 기억 5(래치·타이머·엣지·카운터·홀드) · 행동 7 을
문장으로 덮는다. PID·범위제한·둘중고르기·상태기계와 깊은 조합만 그림 쪽에 남는다.
규칙끼리는 **이름으로**
잇는다 — `규칙 1: … → [전기부족]` 을 `규칙 2: 만약 [전기부족] 이고 …` 가 읽는다. 배선 없이
조합되고, 무엇보다 읽을 수 있다.

### 한 방향인 이유

문장 → 회로는 되고 회로 → 문장은 **안 된다.** 노드를 손대는 순간 그 제어기의 문장 화면은
잠긴다. 같은 것을 고르는 규칙이 두 곳에 있으면 반드시 갈리기 때문이다 — 인서터의
peek 과 take 가 서로 다른 아이템을 고르던 그 실패가 원형이고, 그때 공급 라인이 통째로
죽었다. 조용히 갈리는 것보다 한쪽을 잠그는 편이 낫다.

세 가지는 원장에서 그대로 옮겨 왔다: 연구가 안 된 노드로는 **컴파일하지 않는다**
(잠긴 노드는 evalNode 가 조용히 0 을 내서 "문장은 맞는데 아무 일도 안 일어남"이 된다) ·
확인 대화상자를 쓰지 않는다(헤드리스가 서고 UX 도 나쁘다) · 컴파일이 노드에 주는 좌표는
결정론적이다(좌표가 곧 평가 순서라, 흔들리면 같은 문장이 판마다 다르게 돈다).

만들면서 두 가지가 더 드러났다. 인라인 `onclick` 은 전역만 보므로 IIFE 안의 함수를 그대로
쓰면 버튼이 **조용히 죽는다.** 그리고 `entName` 이 없는 대상에 `null` 대신 "(대상 고르기)"
를 돌려주게 바꾼 순간, 그 값으로 "대상 없음"을 판정하던 안전 검사가 영원히 안 걸리게 됐다 —
**표시용 함수를 술어로 쓰면 표시를 고칠 때 판정이 따라 죽는다.**

## 기차 — 먼 광맥을 쓸 이유

광맥은 멀수록 크고 풍부한데(`10_world.js` 는 그렇게 생성한다), 벨트로 60타일을 끌면
벨트값이 광석값을 넘는다. 기차는 그 거리를 값싸게 만든다.

레일을 깔고, 레일 **옆**에 역을 세우고, 레일 **위**에 열차를 놓는다. 열차는 닿을 수 있는
역들을 지은 순서대로 돌고, 싣고 내리는 것은 인서터가 한다 — **역에 선 열차는 움직이는
상자**라, 인서터가 대상을 푸는 자리 한 곳만 열어 주면 적재가 통째로 붙는다.

| 항목 | 값 | 근거 |
|---|---|---|
| 속도 | **8 타일/s** | **설계값.** Factorio 기관차는 82 타일/s 인데 이 맵은 한 변이 160타일이라 그대로 쓰면 2초에 횡단한다. 8이면 횡단 20초, 벨트(1.875)의 4.3배 |
| 화물 | 2000개 | 상자(600)의 3.3배 — 한 번에 옮길 값이 있어야 한다 |
| 정차 | 5초 뒤 자동 출발 | 배선 없이도 게임이 돌아야 한다 |

### 언제 떠나는가 — 그게 이 게임의 자리다

기본은 "화물이 다 찼거나 5초가 지나면 간다". 그런데 역에 제어기의 **[열차 출발]** 노드를
물리면 **그 역은 제어기가 정한다** — 참이면 보내고 거짓이면 붙잡는다. 다른 출력 노드와 같은
규약이다(안 물리면 지배하지 않고, 노드를 지우면 지배가 풀린다).

읽는 쪽은 **[역 상태]**(열차있음 · 화물 · 화물%). 둘을 합치면 "도착지 상자가 빌 때까지
붙잡았다가 보낸다" 같은 배차가 회로가 된다.

게이트는 **기본값과 반대 방향**으로 잰다 — 기본이 "5초 뒤 출발"이므로, 허가를 거짓으로
물려 두고 12초를 돌려 **여전히 x=40 에 붙잡혀 있는지** 본다. 그 다음 허가를 참으로 바꿔
즉시 떠나는 것까지 확인한다(조건 발생 확인).

### v1 이 아직 안 하는 것

**신호기 · 다중 편성 · 교차 통제 · 대각선 곡선이 없다.** 그래서 **한 노선에 열차 한 대**를
전제한다 — 같은 레일에 두 대를 놓으면 서로를 통과한다. 레일은 격자 위 1×1 타일이고 직각
코너까지만 된다(벨트와 같은 규약). 연료도 안 먹는다. 넷 다 "아직 안 만든 것"이지 "안 되는
것"이 아니고, 넣을 때는 신호기부터다.

열차는 **점유맵 밖**에 산다. 한 칸에는 엔티티 id 하나뿐인데 그 자리는 레일이 쓰고 있어서,
열차를 넣으면 지나갈 때마다 레일의 점유가 지워진다. 대신 `trainAt()` 로 찾고 인서터가
대상을 푸는 네 함수에서만 그것을 본다 — 그래서 배치 경로도 갈린다(레일 위에만 놓인다).

## 청사진 — 잘 도는 라인을 통째로 늘린다

`B` (폰은 [청사진] 버튼) 로 영역을 끌어 담고, 좌클릭 한 번으로 붙인다. 놓일 자리는 미리
파랗게, **못 놓는 칸은 빨갛게** 보인다 — 붙이기 전에 몇 개가 건너뛸지 알 수 있다.

**이 기능의 값은 배선이다.** 벨트와 기계만 복사하는 것은 편의지만, 제어기의 규칙과 노드
그래프가 따라오면 "잘 도는 라인 하나"를 통째로 늘릴 수 있다. 그래서 참조 처리에 규칙이 있다:

- 영역 **안**의 기계를 가리키던 참조는 **사본의 기계로 갈아 끼운다.**
- 영역 **밖**을 가리키던 참조는 **끊는다**(`(대상 고르기)` 상태). 안 끊으면 붙여넣은 사본이
  원본의 기계를 지배하고, 플레이어는 왜 멈췄는지 짚을 수 없다. Factorio 도 같은 규칙이다.

게이트가 그 둘을 한 번에 잰다 — 사본 상자를 비우면 **사본** 조립기가 켜지고, 동시에 원본
상자를 채우면 **원본** 조립기가 꺼진다. 사본이 원본을 지배하면 이 두 값이 뒤집힌다.

세 가지를 더 못 박았다.

- **재료는 실제로 나간다.** `placeEntity(free=false)` 로 짓는다 — 공짜면 청사진이 치트다.
- **내용물은 안 따라온다.** 상자 재고·벨트 위 아이템·연료는 계획이 아니라 화물이고,
  따라오면 청사진이 복제기가 된다(물질수지가 깨진다).
- **전부-아니면-전무가 아니다.** 막힌 칸·모자란 재료는 그 항목만 건너뛰고 나머지를 짓되,
  몇 개를 왜 건너뛰었는지 돌려준다. 큰 청사진이 한 칸 때문에 영영 안 붙는 것이 더 나쁘다.

**회전은 `R`(폰은 [회전] 버튼)로 90도씩.** 좌표와 **방향을 함께** 돌린다 — 하나만 돌리면
라인 모양은 맞는데 흐름이 옛 방향이거나(좌표만), 제자리에서 엉뚱한 곳을 가리킨다(방향만).
크기는 정의값이 아니라 **지금 방향 기준의 실제 발자국**을 쓴다. 분배기는 2x1 인데 방향
1·3 에서는 1x2 로 서기 때문에(`canPlace` 가 그렇게 정한다), 정의값을 그대로 쓰면 회전 뒤
자리가 한 칸 어긋난다.

게이트를 세울 때 두 번 헛디뎠고 둘 다 돌연변이가 짚었다. **담는 영역을 4x4 로 잡았더니**
`rotateSwapsFootprint` 가 "4x4 → 4x4" 로 통과했다 — 정사각형에서는 가로세로가 바뀌어도
같은 수다. 그리고 리그에 **방향 1 짜리 분배기가 없어서** 발자국 규칙을 지우는 돌연변이가
그대로 살아남았다(MISS) — 규칙이 적용되는 입력이 없으면 그 규칙은 검정되지 않는다.

`R` 은 원래 도구 방향을 돌리는 키다. 붙여넣기 중에는 손에 든 것이 도구가 아니라
청사진이므로 그쪽을 돌린다. **키와 [회전] 버튼이 같은 손잡이(`rotateAction`)를 쓴다** —
키 쪽에만 갈림길을 넣었더니 키보드가 없는 기기에서 청사진 회전이 통째로 닿지 않았고,
그건 터치 게이트가 잡았다.

## 증기 발전 — 버퍼가 생기면 제어가 달라진다

강철 제련이 **파이프 · 지하수 펌프 · 보일러 · 증기기관**을 함께 연다. 맞대어 놓으면 한
유체망이고(전력망의 유니온-파인드를 그대로 이식했다), 파이프 한 칸을 빼면 그 자리에서
끊긴다. 망 하나는 **잘 섞인 탱크 하나**로 다룬다 — 압력 기울기도 흐름 방향도 없다.
전력망이 선로 손실을 모형화하지 않는 것과 같은 층위의 단순화다.

수치는 여기서도 Factorio 공개값이고, **넷이 하나의 항등식으로 묶여 있다**:

| 설비 | 값 |
|---|---|
| 지하수 펌프 | 1200 물/s · 전기 안 씀 |
| 보일러 | 1.8 MW 로 물 60/s → 증기 60/s |
| 증기기관 | 증기 30/s → 900 kW |
| 파이프 | 한 칸에 100 저장 |

`1800 ÷ 60 = 30 = 900 ÷ 30` — **증기 1개가 양쪽에서 똑같이 30 kJ** 이다. 게이트는 이
항등식을 오라클로 쓴다: 실측 `태운 에너지 ÷ 만든 증기 = 30.00 kJ/증기`. 넷 중 하나만
바꿔도 즉시 어긋난다.

효율은 발전기와 같다(둘 다 100%). 얻는 것은 두 가지다 — **석탄 넣는 곳이 절반**
(보일러 1대가 증기기관 2대를 먹인다)이고, **파이프에 증기가 고인다.**

### 고인 증기가 요점이다 — 선행 지표가 생긴다

발전이 한 단계에서 두 단계가 되면 중간에 저장고가 생긴다. 그래서 두 가지가 달라진다.

- 석탄이 끊겨도 증기가 남아 있으면 전기는 버틴다. 실측: 석탄 1개(4000 kJ)를 넣고 다 태운 뒤
  (`연료 0 kJ` 확인) 남은 증기 133 으로 **0.5초 뒤에도 900 kW** 를 유지한다.
- 반대로, 부하가 몰리면 **전기가 흔들리기 전에 증기부터 준다.** 실측: 수요 858 kW(공급 900
  아래)에서 증기가 50% 밑으로 내려간 순간 전력 만족도는 아직 **100%** 였고, 전력이 처음
  무너진 순간 증기는 이미 **0%** 였다.

두 번째가 이 계를 넣은 이유다. 전력 만족도는 **이미 모자란 뒤에야** 떨어지는 사후 지표지만,
증기%는 그 전에 내려가는 **선행 지표**다. 제어기의 과제가 "전기가 모자라면 끄기"에서
**"증기가 마르기 전에 끄기"** 로 옮겨 간다 — 되먹임 제어에서 미분항을 얻는 것과 같은
성격의 변화이고, 이 게임이 가르치려는 지점이 정확히 거기다.

읽는 것은 **유체 잔량** 노드(증기% · 증기 · 물 · 망연결)이고, 문장 편집기에도 `증기 잔량`
으로 있다. 하고 싶은 일 카드 **"증기가 마르기 전에 미리 끄기"** 가 그 회로를 절반 채워서
연다(래치 + 20초 복구 지연 — 되먹임계라 그냥 임계값만 쓰면 발진한다, `tasks/lessons/07`).

> **물 지형은 넣었다가 되돌렸다.** Factorio 처럼 호수를 만들고 펌프를 물가에만 세워 봤는데,
> 시험 리그들이 고정 좌표에 짓기 때문에(스폰에서 최대 85타일) 호수가 그 자리를 덮으면
> 드라이버가 통째로 죽었다. 물가 배치 퍼즐은 여기서 얻으려던 것(증기 버퍼로 깊어지는 제어
> 문제)과 무관해서, 지형 대신 규칙을 단순화했다 — 펌프는 어디에나 서는 지하수 펌프다.
> 자세한 것은 `tasks/failure-ledger.md`.

### 이송 펌프 — 두 망을 합치지 않고 옮긴다

파이프로 이으면 그 순간 **한 망**이 되어 "저쪽이 찰 때까지 이쪽을 비운다" 를 할 수 없다.
이송 펌프는 뒤쪽 망에서 빨아 앞쪽 망으로 200/s(Factorio pump 공개값) 밀되 **두 망은
끝까지 남남**이다 — 그래서 *언제 옮길지* 를 제어기가 정할 수 있고, 그것이 이 건물이 여는
새 결정이다. 전기를 쓴다(취수 펌프는 자기강화 고장을 막으려 일부러 안 쓰지만, 이쪽은
멈춰도 물이 끊기지 않는다).

게이트의 첫 줄이 **"망이 2개인가"** 인 이유가 그것이다 — 회원으로 넣어 유니온-파인드가
앞뒤를 합쳐 버리면 이 건물의 존재 이유가 사라지고, 그 돌연변이가 정확히 그 게이트를
뒤집는다.

완주 주행에 넣으면서 자리 조건으로 두 번 헛디뎠다. 처음엔 탱크(3x3)를 한 칸 띄워 그쪽을
두 번째 망으로 삼으려 했는데 **두 자리를 동시에 요구하니 맞는 열이 없어** 탱크조차 못
세웠다(건물 21종 → 20종). **파이프 한 칸이면 망 하나다** — 펌프 앞에 파이프를 한 칸 두는
것으로 바꾸자 자리 조건이 3x3 에서 두 칸으로 줄어 들어갔다.

### 저장 탱크 — 완충을 얼마나 둘 것인가

파이프 한 칸이 100 인데 **탱크는 25,000**(Factorio 저장 탱크의 공개값)이다. 파이프
250칸어치라, 증기 60/s 를 쓰는 보일러 기준으로 7분 가까이 버틴다. 완충이 크면 제어기가
늦게 반응해도 되고 작으면 빨라야 한다 — **얼마나 둘 것인가가 설계 결정이 된다.**

게이트의 오라클은 두 가지다. 용량은 설계값 25,000 을 **시험 파일에 숫자로 박아** 댄다
(게임에서 읽으면 상수를 바꿔도 양변이 같이 움직인다). 그리고 **완충은 곧 시간이다** —
연료를 끊은 뒤 버티는 시간이 `저장량 ÷ 소비(30/s)` 여야 한다(실측 837 → 27초, 예상 28초).

그 게이트를 세우면서 세 번 헛디뎠다. **전기 수요가 없으면 증기기관은 증기를 안 쓴다** —
부하를 안 걸고 쟀더니 400초(측정 상한)를 그대로 버텼고, 그 판의 "오래 간다"는 아무것도
증명하지 않았다. 부하를 걸었더니 이번엔 **조립기의 출력 버퍼가 차서** 수요가 사라졌다 —
차면 멈추는 부하는 부하가 아니다. 마지막으로 3x3 탱크를 보일러와 겹치는 자리에 두어
배치가 조용히 실패했는데, 게이트에는 "용량이 안 늘었다"로만 보였다 — 배치 실패와 용량
계산 오류가 같은 얼굴을 한다. 지금은 배치 여부를 메시지에 같이 찍는다.

### 최고·최저 기록 — 완충을 얼마나 둘지는 최악치가 정한다

저장 탱크가 들어오면서 "완충을 얼마나 둘 것인가" 가 플레이어의 설계 결정이 됐다. 그
결정의 근거는 **"이번 판에서 증기가 가장 낮았을 때 몇 %였나"** 인데, 순간값은 눈 깜짝할
사이에 지나간다. 이 노드가 대신 기억한다. 리셋을 물리면 그 순간부터 다시 재고, **리셋이
값보다 우선한다**(래치의 RESET 과 같은 규약).

**함정은 씨앗이다.** 최저 기록을 0 에서 출발시키면 0 보다 낮은 값이 없어 영원히 0 을 낸다 —
평활 필터가 겪은 것과 같은 부류다(교훈 15). 첫 실제 입력에서 출발하고, 그 성질을 겨냥한
돌연변이(씨앗을 0 으로 박기)가 게이트를 실제로 뒤집는 것까지 확인했다.

문장 편집기에는 넣지 않았다 — 문장 한 줄은 "조건 하나에 행동 하나" 인데 기록은 값
변환이라 한 줄로 접히지 않는다(상태기계를 뺀 것과 같은 이유다).

### 지속 조건 — 늦추는 것이 아니라 확인하는 것

`조건이 N초 이상 계속돼야` 참이 된다. **평활 필터와 자리가 다르다** — 평활은 값을 눅여서
모든 반응을 늦추는 대신 진짜 변화도 늦게 알리고, 지속은 값을 안 건드린 채 짧은 튐만
버린다. 3초를 넘기는 순간 바로 참이 되므로 지연이 아니라 확인이다. 조건이 한 번 끊기면
시계는 0 으로 돌아간다 — **'누적'이 아니라 '연속'** 이라야 한다(그 성질이 게이트의 오라클이고,
시계를 안 지우는 돌연변이가 거기서 걸린다).

문장 편집기의 기억 자리에서 `초 이상 계속되면` 으로도 고를 수 있다.

### 변화율 — 얼마나 남았나가 아니라 얼마나 빨리 줄고 있나

완충(저장 탱크)이 커질수록 **수위 자체는 느리게 움직여 신호로 약해진다.** 그때 쓸 수
있는 것이 기울기다: 증기가 초당 12씩 줄고 3,000 남았다면 250초 뒤에 마른다 — 그 나눗셈은
[계산] 노드가 이미 하고, `변화율` 노드는 그 분모를 만든다. `평활 창 s` 로 튀는 값을 눅이고,
0 이면 날것이다. 문장 편집기에서도 `초 창으로 잰 초당 변화` 로 고를 수 있다.

**오라클을 두 번 갈아 끼웠다.** 처음엔 타이머의 `위상%` 를 썼다 — 주기 동안 0→100 을
선형으로 오르니 기울기가 정확히 100/주기 라고 본 것이다. 그런데 그 출력은 **정수로
반올림**된 계단이라(`Math.round`) 대부분의 틱에서 변화가 0 이고 가끔 1 씩 뛴다. 날것의
변화율이 0.000 으로 나왔고, 평활을 걸었더니 주기 경계의 100→0 이 튀어 음수가 됐다 —
**계단을 미분해 놓고 미분이 틀렸다고 읽을 뻔했다.** 취수 펌프가 붓는 물(1200/s, 반올림
없는 연속량)로 바꾸자 1200.0 이 나왔다.

문장 편집기 쪽에도 갈림길이 생겼다. 단항 계산이 `눅이기` 하나뿐이던 시절 컴파일러가
`smooth` 를 손으로 박아 두고 있어서, 그대로 두면 **변화율을 골라도 평활이 걸린다.**
정의에 노드 이름과 설정 열쇠를 적어 컴파일러가 그것을 읽게 했고, 돌연변이로 그 갈림길이
실제로 갈리는지 확인했다.

## 신호를 다듬고, 나누고, 단계로 쪼갠다

노드 셋을 더 얹었다. 셋 다 "제어기로 무엇을 할 수 있는가"를 넓히는 쪽이지, 새 건물이나
새 자원이 아니다 — 이 게임의 차별점은 거기에 있다.

**평활 필터** (논리 III). 1차 저역통과다. `시상수 τ` 는 입력이 계단으로 바뀌었을 때 63% 를
따라가는 데 걸리는 시간이고, 계단응답은 `y(t) = 1 - e^(-t/τ)` 그대로다. 재고나 전력
만족도처럼 매 틱 튀는 값을 임계값 비교에 바로 물리면 경계에서 딸깍거리는데, 한 단 끼우면
잦아든다 — 대신 반응이 느려진다. 그 맞바꿈이 이 노드의 전부다.

구현은 오일러 근사(`(x-y)·dt/τ`)가 아니라 **지수해**(`(x-y)(1-e^(-dt/τ))`)다. 이유는 정확도가
아니라 검증이다: 지수해는 같은 게임시간을 어떻게 쪼개도 같은 값을 내므로, "1초를 60틱으로
민 값 == 4틱으로 민 값" 이 곧 *dt 를 곱했는가* 를 묻는 게이트가 된다. 매 틱 누적에서 `dt` 를
빠뜨려 오염이 60배 나왔던 실패(`tasks/lessons/03`)와 같은 축이라, 그 축에 오라클을 박았다.

**상태기계** (논리 II). 공정을 1→2→3→4→1 로 돌린다. 각 전이 입력은 그 단계에 있을 때만
보고, **거짓에서 참으로 올라가는 순간**에만 넘어간다 — 조건을 참인 채로 두어도 한 칸이다
(레벨로 두면 60 Hz 로 단계가 돌아 버린다. 카운터의 `증가` 입력이 이미 같은 규약이다).
리셋은 레벨이고 전이보다 우선한다. 단계 출구 넷은 그 단계에서만 1 이라 기계를 바로 물릴 수
있다: 타이머를 전이에 물리면 순서 반복, 재고 조건을 물리면 재고가 이끄는 공정이 된다.

**신호 버스** (논리 III). 제어기끼리 값을 주고받는 8채널(A~H)이다. 규칙은 둘뿐이다.

- **같은 채널에 여러 제어기가 보내면 합산된다.** 마지막 값이 이기게 하면 제어기 평가
  순서가 값을 정하는데, 제어기 사이의 순서는 배치로 정해지지 않는다 — 플레이어가 원인을
  짚을 단서가 하나도 없어진다. 합은 순서와 무관하다.
- **받는 값은 언제나 직전 틱 값이다.** 같은 이유이고, 되먹임 배선이 쓰는 규약과 같다.

채널 이름은 자유 입력이 아니라 고정 목록이다. 오타 하나로 조용히 침묵하는 것이 이 게임에서
가장 나쁜 실패라, 출력 노드의 대상 목록을 "실제로 그 값을 읽는 건물"로 좁힌 것과 같은
원칙을 적용했다. 송신 노드를 지우면 그 몫은 다음 틱에 바로 빠진다(출력 축의 유령 지배
해제와 같은 성질).

### 문장으로도 쓴다 — 셋 중 둘만

평활 필터와 신호 버스는 **문장 편집기에도 들어갔다.** 읽을 것 옆에서 `(그대로)` 를
`초로 눅인 값` 으로 바꾸면 그 값이 눅고, 행동에서 `다른 제어기에 신호를 보낸다` 를
고르면 잰 값이 채널로 나간다. 받는 쪽은 읽을 것에서 `받은 신호` 를 고른다.

```
규칙  [전기여유알림]
  만약  전기 여유 를 5초로 눅인 값 이 -1000000000kW 이상이면
  그래서 채널 A 로 다른 제어기에 신호를 보낸다
```

**상태기계는 넣지 않았다.** 문장 한 줄은 조건 하나에 행동 하나인데 상태기계는 전이가
넷이다 — 한 줄로 접으면 문장이 아니라 표가 된다. 억지로 넣는 대신 도움말에 "이건 회로
화면에서 쓴다"고 적었다.

넣으면서 문장 쪽에서 두 가지가 더 드러났다. **'숫자를 화면에 띄운다' 가 숫자를 안 띄우고
있었다** — 행동표의 `value` 플래그를 컴파일러가 한 번도 안 읽어서, 조건의 참/거짓(1 또는 0)
이 화면에 떴다. "숫자를 화면에 띄워 보기" 카드가 정확히 그 상태였다. 이제 값을 받는 행동은
`[선택]` 한 단을 거쳐 **조건이 참이면 잰 값, 아니면 0** 을 받는다.

그리고 **계산 한 단(`when.math`)에는 화면에 고를 자리가 아예 없었다.** 컴파일러도 되읽기도
진작부터 지원했는데 드롭다운이 없어서 카드로 만든 규칙 말고는 아무도 쓸 수 없었다. 이
레포는 같은 실패를 저장/불러오기에서 한 번 했다 — **진입점이 없는 기능은 없는 기능이다.**
드롭다운과 숫자 칸을 붙이고, 그 경로를 클릭으로 검사한다(`ui.mathDropdownExistsAndCompiles`).

### 게이트 19건이 GREEN 인 다음에 적대적 리뷰가 잡은 것

게이트를 다 통과시킨 뒤 다섯 렌즈(버스 의미론 · 필터 수치 · 상태기계 · 게이트 품질 ·
통합 회귀)로 리뷰를 돌리고, 올라온 지적마다 **반증을 시도하는** 검증을 따로 붙였다.
43건 중 33건이 반증으로 떨어지고 10건이 남았다. 그중 둘이 무거웠다.

**씨앗 심기가 자기 목적을 배반했다.** 평활 필터의 첫 평가는 `y = 입력값` 으로 출발한다 —
이미 돌던 신호에 필터를 물릴 때 0 에서 기어오르는 과도를 막으려는 것이다. 그런데 사람이
노드를 만드는 경로는 팔레트 클릭뿐이고 그때 노드는 **배선 없이** 생긴다. 편집기를 열어도
시뮬은 돌고 고립 노드도 평가되므로, 16.7 ms 안에 입력 0 으로 첫 평가가 돌아 `y = 0` 이
박힌다. 그 뒤 배선하면 재씨앗이 안 되고 **막으려던 과도가 정확히 그 자리에서 생긴다**
(τ=10·재고 60·임계 50 이면 거짓 경보 17.9초). 게이트 넷이 전부 배선을 첫 틱 전에 끝내고
입력을 0 으로 뒀던 탓에 "입력값 씨앗"과 "0 씨앗"이 구별되지 않았다. 출력 노드들이 이미
쓰는 규약(`안 물린 입력은 지배하지 않는다`)을 상태를 가진 연산 노드에도 적용해 고쳤다.

**두 결함이 서로를 가려 저장 게이트가 GREEN 을 냈다.** 상태기계 저장 검사를 2단계에서
했는데, 저장 시점에 전이 조건이 참으로 붙들려 있었다. 노드 상태를 통째로 잃은 구현은
복원 시 1단계로 초기화되고, 붙들린 조건이 상승엣지로 읽혀 한 칸 튀어 **정확히 2단계**에
도착한다 — `2 === 2` 라 통과다. 저장 지점을 3단계로 옮기고 조건을 내린 채 저장하도록
바꾼 뒤, "엣지 기억이 남는가"는 조건을 **든 채** 4단계에서 저장하는 별도 검사로 쪼갰다.

나머지 여덟은 전부 같은 모양이었다 — **리그가 한 번도 데려가지 않은 상태.** 상태기계
게이트가 3단계까지만 갔고(4단계도 4→1 순환도 무검정), 네 전이 입력을 한 신호에 묶어 둔
탓에 "각 입력은 그 단계에서만 유효하다"는 정의 자체가 안 재졌고, 버스 리그는 수신
제어기를 늘 마지막에 만들어 검출이 배치의 우연에 얹혀 있었다. 게이트를 7건 더 넣고
그 7건을 겨냥한 돌연변이 6건을 추가해 **전부 실제로 뒤집히는 것까지** 확인했다.
자세한 것은 `tasks/lessons/15`.

## 알려진 한계

- **증기 발전과 기차는 있다.** 석유·화학은 없다.
- 기차에 **신호기·다중 편성·교차 통제**가 없다 — 한 노선에 한 대를 전제한다.
- 유체망은 **잘 섞인 탱크 하나**로 다룬다 — 압력 기울기도, 흐름 방향도, 펌프 양정도 없다.
- 물 지형이 없다. 펌프는 지하수를 뽑는 것으로 두었다(위 절의 상자 참고).
- 지하 벨트가 없다. 대신 분배기와 벨트 게이트가 있다.
- 플레이어 아바타가 없다 — 당신은 제어계이지 사람이 아니다. 이동 제약이 없는 대신
  건설 범위 제한도 없다.
- **제어기는 전기를 쓰지 않는다.** 전력을 요구하면 부하 차단 배선이 자기 전원을 끊고
  자멸한다(Factorio의 회로망도 같은 이유로 무전력이다).
- 저장은 `localStorage` 한 칸. 여러 슬롯은 없다. `F2`/`F3` 또는 창고 패널 버튼.
  **40분 판이 175 KB** 이고(대부분 지형 배열 — 엔티티 12개짜리 빈 판도 141 KB 다) 브라우저가
  주는 칸은 대략 5 MB 다. 게이트가 1 MB 를 상한으로 지킨다(`clear.saveFitsBudget`).
  저장칸이 거부하면(할당량 초과·사생활 모드) 코드가 잡아서 알리고 판은 그대로 둔다 —
  그 처리 자체를 검정하는 게이트를 이번에 세웠다(`save.survivesQuotaFailure`). 예전에는
  처리는 있는데 게이트가 없어서, 다음 수정에서 조용히 사라져도 아무도 몰랐을 자리였다.
- 검증은 헤드리스 4엔진(Edge·Chromium·Firefox·WebKit) 기준이다. **실기 Safari 와 실기 모바일,
  그리고 "재미"는 미검증** — 페이싱 표는 규칙이 맞는지만 보여주고 재미는 못 잰다.
- 터치는 있다(폰·태블릿 레이아웃, 노드 편집기 터치 배선, 모바일 조작 바, 홈화면 설치).
  다만 자동 검증은 chromium 의 mobile·tablet 에뮬레이션 두 조합뿐이고, webkit·firefox 는
  합성 터치를 못 만들어 미검증이다. **실제 기기에서는 아직 아무도 안 만져 봤다** — 설치도
  마찬가지로, 재료가 갖춰졌다는 것까지만 확인했다.
- 신호 버스는 8채널 고정이고 값은 실수 하나다. 이름표·품목 같은 것은 못 보낸다.
- 새 노드 셋 중 **상태기계만** 문장 편집기에 없다(전이가 넷이라 한 줄로 안 접힌다).
  평활 필터와 신호 버스는 문장으로도 쓴다.
- 페이싱 측정은 "기계가 굶지 않는 완벽한 공장" 가정 위의 **상한**이다. 실제 플레이는 더 느리다.
