# 커버리지 게이트는 기준을 스스로 올린다 — 따라 올리지 않으면 구멍이 생긴다

기차를 붙이고 모델 209 · 클릭 78 · 전수 37 · 돌연변이 130 을 전부 GREEN 으로 맞춘 뒤,
40분 완주 주행을 돌렸더니 11건 중 4건이 RED 였다. 둘은 원래 그랬고, **둘은 내가 만든
것이었다.**

```
건물 13/20종 사용 · 안 쓴 것: pipe,pump,boiler,rail,station,train,engine
노드 29/32종 배선 · 안 쓴 것: fluid,station,traingo
```

## 1. 기준이 저절로 오르는 게이트가 있다

이 두 게이트는 기대값을 **게임의 목록에서** 읽는다.

```js
var allTypes = G.buildingTypes();
var missingB = allTypes.filter(function (ty) { return !built[ty]; });
```

교훈 16 은 "기대값을 재는 대상에서 읽지 마라"였는데, 여기서는 그게 맞다 — 이건 값을
대조하는 오라클이 아니라 **커버리지**를 재는 게이트이고, "게임에 있는 모든 것"이 곧
기준이기 때문이다. 값 오라클과 커버리지 게이트는 같은 규칙을 따르지 않는다.

대신 다른 함정이 있다: **기능을 늘리면 기준이 저절로 올라간다.** 유체 4종·철도 3종을
넣는 순간 기준이 13 → 20 이 됐고, 드라이버는 13 에 머물렀다. 로직 노드를 늘릴 때는
지켰던 규율(25→29 로 주행도 같이 늘렸다)을 유체·기차에서 **연달아 두 번** 놓쳤다.

> 기능 추가의 완료 정의에 **"완주 드라이버 확장"**이 들어가야 한다.
> 모델 게이트가 전부 GREEN 이어도 그 기능은 플레이어의 40분에 한 번도 안 나온다.

## 2. 지었다 ≠ 돈다

커버리지 게이트는 **배치한 순간**을 센다. 연료 없는 보일러도, 한 발짝도 안 움직인
열차도 통과시킨다. 그래서 게이트를 둘 더 세웠다.

```
clear.steamPlantRan   증기 최대 잔량 > 0
clear.trainRanRoute   열차 이동 누적 ≥ 10 타일
```

첫 실행에서 둘 다 RED 였다 — 설비가 아예 안 지어졌으니 당연하고, **그게 이 게이트가
비어 있지 않다는 증거다.** 통과만 하는 게이트를 새로 다는 것이 이 레포에서 반복되는
실패라, 새 게이트는 처음에 반드시 빨간불을 봐야 한다.

## 3. 흐름이 넉넉한 것과 재고가 있는 것은 다르다

증기 발전소를 못 짓는 이유가 40분 내내 `철판 0/40` 이었다. 그런데 이 공장은 철판을
초당 여러 장 만든다. 재고가 0 인 이유는 생산이 아니라 **소비 순서**였다.

```
harvest → craft(다 쓴다) → ... → feed(기계 버퍼로 밀어 넣는다) → runStages(여기서 잔고를 본다)
```

셋을 고쳐야 살 수 있었다.

- **줄의 앞에 선다** — 구매 단계를 `craft` 앞으로 옮겼다. 이 파일의 주석이 이미
  말하고 있었다: "한 사이클 안의 순서가 곧 우선순위다."
- **안 없어지는 형태로 저축한다** — 파이프 아이템은 이 판의 어느 기계도 재료로 안 쓴다.
  철판으로 두면 다음 사이클에 사라지고, 파이프로 바꿔 두면 남는다.
- **부품별로 사되 자리는 못 박는다** — 처음엔 부품별로 사면서 실패할 때마다 자리를
  새로 찾았다. 그래서 펌프·보일러를 40분 동안 반복해 짓고 철판이 0 이 되어 탄약까지
  끊겼다(손실 3 → 7). **누수의 원인은 부분 건설이 아니라 자리를 바꾼 것이었다.**

## 4. 목표를 올릴 때 같이 안 오른 상수가 조용한 상한이 된다

강철 목표를 4 → 24 로 올렸는데 40분에 11개에서 멈췄다. 원인은 제련이 아니라
`feed` 의 재고 상한표였다.

```js
var CAP = { …, steel: 8 };   // 분배기(강철 2)만 있던 시절의 값
```

강철 재고가 9 가 된 순간 이 줄이 제련로를 **영원히 건너뛰게** 했다. 증상은 "강철이
안 모인다"인데 원인은 "제련로가 재료를 안 받는다"라, 재고만 봐서는 절대 안 보인다.
진단 문구를 `재고` 한 줄에서 `재고 · 누계 제련 · 제련로 상태` 세 줄로 늘리자 즉시
갈렸다 — `강철 9/20 · 누계 제련 11 · 제련로 steel(정지)`.

> 목표량과 상한은 **같은 식에 묶는다** (`steel: STEEL_WANT + 4`).
> 진단은 재고가 아니라 **누계 생산 + 설비 상태**로 남긴다.

## 5. 새 설비는 기존 자원의 경쟁자다

보일러를 발전기와 같은 순위로 먹였더니 최저 전력 만족도가 47.2% 로 떨어져 보였다.
보일러는 1.8 MW 를 태워 900 kW 를 낸다 — 발전기보다 석탄 효율이 **나쁘고**, 그 대가로
버퍼를 얻는 설비다. 그래서 발전기를 먼저 먹이고 석탄 재고가 40 을 넘을 때만 보일러에
조금씩 주도록 바꿨다. 근거는 물리이지 그 숫자가 아니다 — 아래 6절에서 드러나듯 전력
만족도는 주행마다 46~94% 로 흔들려서, **한 판의 개선/악화로는 아무것도 못 보인다.**

> 새 설비를 넣을 때는 그것이 **무엇을 나눠 먹는지**를 먼저 적는다.
> 여기서는 석탄이었고, 손해로 보인 것은 기능이 아니라 순서였다.

## 결과

```
건물 20/20 · 노드 32/32 · 증기 최대 잔량 1199.8 · 열차 이동 65~97 타일
→ 커버리지 4건은 6회 주행에서 한 번도 안 흔들렸다
남은 RED: 연구 5~6/8 · 습격 손실 3~10 · 최저 전력 46~94%
→ 뒤의 둘은 아래 6절대로 재현이 안 된다. 이 판정은 아직 못 믿는다.
```

## 6. 덤으로 드러난 것 — 이 주행은 재현되지 않는다

커버리지를 메우고 나서 "연속 2회 같은 결과"를 확인하려다 알았다. **코드를 한 글자도
안 바꾸고 6번 돌렸는데 6번 다 달랐다.** 습격 손실 3·7·8·10, 최저 전력 46.1~94.3%.
`powerHeld` 게이트가 주행마다 PASS 와 FAIL 을 오간다.

> **뒤집히는 게이트는 게이트가 아니다.** 그 숫자로는 어떤 비교도 못 한다.

여기까지 좁혔다.

- 게임에 이미 있던 `G.stateHash()`(엔티티별 재고·진행도까지 포함)로 지문을 찍으니
  **갈리는 시각 자체가 주행마다 다르다** — 어떤 쌍은 t=900, 어떤 쌍은 t=1500.
- **가설 하나를 반증했다.** "일시정지 중에도 도는 렌더·UI 프레임이 시뮬을 건드린다"고
  보고, 드라이버가 40분을 한 번의 동기 실행으로 밀어 프레임을 아예 안 끼워 넣게 했다.
  그래도 갈렸다. 프레임은 범인이 아니다.
- **내가 만든 것이 아니다.** `git show HEAD:tests/clear.js` 로 변경 전 드라이버를 두 번
  돌렸더니 전력 47.9% 와 90.7% 가 나왔다 — README 가 "작은 변경에도 궤적이 흔들린다"며
  버전 차이로 설명하던 그 두 숫자가, 실은 같은 코드의 두 주행이었다.

**교훈은 반증 자체보다 그 앞이다.** 나는 "이 주행은 결정론적이다"라는 문서의 주장을
그대로 믿고 여섯 번을 비교 근거로 쓰려 했다. 재현성은 **주장이 아니라 측정**이어야 하고,
가장 싼 측정은 *같은 것을 두 번 돌려 보는 것*이다.

> 어떤 수치를 근거로 쓰기 전에 **같은 조건에서 두 번 재라.**
> 그게 안 맞으면 그 수치로는 아무것도 비교할 수 없다 — 결론이 아니라 측정이 문제다.
