# 오라클은 재는 대상 밖에 있어야 한다 — 그리고 창이 좁으면 리그를 넓혀라

기차를 붙이고 게이트 11건을 통과시킨 뒤 돌연변이를 돌렸더니 셋이 살아남았다.
셋 다 코드가 아니라 **게이트가 약했다**. 그중 첫 번째는 이 레포가 처음 겪는 종류다.

## 1. 기대값을 게임에서 읽으면 대조가 아니라 항등식이 된다

속도 게이트를 이렇게 썼다.

```js
var SP = G.spec();                       // 게임이 돌려주는 상수
chk('train.speedMatchesSpec',
    Math.abs(travelSec - 20 / SP.trainSpeed) < 0.12, …);
```

읽으면 그럴듯하다 — 20타일을 속도로 나눈 시간과 실측을 댄다. 그런데
`SPEC.trainSpeed` 를 8에서 12로 바꾸는 돌연변이를 넣었더니 **통과했다.**

당연했다. 값을 바꾸면 열차도 빨라지고 기대값도 같이 빨라진다. 양변이 같은 상수에서
나오므로 차이는 언제나 0 이다. 나는 게임을 **게임 자신과** 대조하고 있었다.

고친 방법은 한 줄이다 — 설계값을 **시험 파일에 숫자로** 박았다.

```js
var TRAIN_SPEED_ORACLE = 8, TRAIN_DWELL_ORACLE = 5;
```

이러면 게임의 수치를 바꿀 때 이 줄도 같이 고쳐야 한다. 그 불편이 바로 오라클의
본질이다 — **두 곳이 독립적으로 같은 값을 주장해야 대조가 성립한다.**

> 게이트를 쓸 때 묻는다: **이 기대값은 어디서 왔는가?**
> 재는 대상과 같은 곳에서 왔다면 그것은 오라클이 아니다.

곁들여: 이 레포의 다른 게이트들도 `SP.*` 를 쓰지만 대체로 무해하다. 벨트는
`beltTilesPerSec / beltSlotGap * 2` 처럼 **파생된** 양을 대조하므로 상수 하나를
바꿔도 양변이 같이 움직이지 않는다. 위험한 것은 여기처럼 관계가 자명해서
(거리 ÷ 시간 = 속도) 정확히 상쇄되는 자리다.

## 2. 관측 창이 0.125초면 그 창에서 재지 마라

"움직이는 열차에는 못 싣는다"를 출발 타일에서 쟀다. 열차가 출발한 뒤 화물이
안 느는지 보는 것이다. 그런데 8타일/s 면 열차가 그 칸을 떠나기까지 **0.125초
(7.5틱)** 뿐이고, 인서터 스윙은 1.2초다. '움직여도 싣는' 구현이 그 좁은 창을
대부분 비켜 가서 돌연변이가 살아남았다.

리그를 바꿔 창을 넓혔다 — **노선 한가운데**에 인서터를 두고 60초(여러 왕복)를
돌렸다. 시뮬레이션이 결정론적이므로, 실으려는 구현은 반드시 한 번은 싣는다.

> 성질이 드러나는 창이 좁으면 **운에 맡기지 말고 리그를 바꿔 창을 넓힌다.**
> "여러 번 돌리면 되겠지"는 확률이지만, 결정론적 시뮬에서는 그게 증명이 된다.

## 3. 이중 방어는 층마다 따로 검정한다

"열차는 레일 위에만 선다"를 UI(`tryPlace`)와 모델(`addTrain`) 양쪽에서 막았다.
좋은 설계다 — 그런데 **한쪽만 깨는 돌연변이는 어느 쪽도 검정하지 못한다.** UI 를
지워도 모델이 막고, 모델을 깨도 UI 가 먼저 막는다. 서로가 서로를 가린다.

이 레포는 같은 형태를 이미 겪었다(`canAccept` 를 while 조건과 giveTo 가 둘 다 보는
자리). 그때의 답은 "둘을 함께 깨는 돌연변이"였는데, 이번에는 두 검사가 **다른
파일**에 있어 한 돌연변이로 묶을 수 없었다.

그래서 반대로 했다 — **각 층을 그 층에서 잰다.** UI 를 거치지 않는 모델 게이트를
따로 세우고(`G.trainAdd(빈 땅) === null`) 모델 검사를 겨냥했다. 이중 방어는
그대로 두었다. 없앨 이유가 없고, 없애면 나쁜 오류 메시지만 남는다.

> 방어가 겹쳐 있으면 **검정도 겹쳐서** 하지 말고, 층마다 그 층을 우회하는
> 경로로 잰다.
