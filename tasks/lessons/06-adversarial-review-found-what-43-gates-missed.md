# 게이트 57건이 전부 GREEN인 산출물에서 적대적 리뷰가 critical 3건을 찾았다 — 게이트는 "내가 생각한 실패"만 막는다

출고(GitHub 푸시) 직전에 5개 차원(시뮬·로직·저장·전투·렌더UI)으로 병렬 코드 리뷰를 돌리고,
발견마다 **반증을 시도하는** 검증 에이전트를 붙였다. 38건이 나왔고 상위 9건을 검증해 9건 전부
반증 실패(=진짜)로 확정됐다. 그때 모델 게이트는 43건, 클릭 게이트는 19건이 전부 GREEN이었다.

## 왜 게이트가 못 잡았나 — 세 가지 패턴

**① 통과 케이스만 있는 설정.** `save.roundtrip` 은 `labSetup()` 의 `giveAll(99999)` 상태에서만
저장했다. 그래서 "자원을 다 쓰고 저장하면 불러올 때 공장이 통째로 사라진다"를 구조적으로
만날 수 없었다. `placeEntity(…, free=true)` 가 비용 **차감**만 건너뛰고 비용 **검사**는 그대로
했기 때문인데, 실제 플레이는 항상 자원을 써서 짓는다 — 즉 거의 모든 진짜 저장본이 그 상태다.

**② 회전의 절반을 아무도 안 밟았다.** 분배기의 두 번째 셀을 `dirCW` 로 잡았는데 점유 사각형의
회전 보정은 dir 1/3 에서만 일어난다. 남·서향 분배기는 셀과 점유가 어긋나 벨트 인계가 막히고
철거가 이웃 건물의 점유를 지웠다. `tests/` 전체에 `splitter` 라는 문자열이 하나도 없었다.
**R 키가 4방향을 도는데 테스트는 한 방향만 썼다.**

**③ 흔한 상태를 특수 케이스로 착각했다.** 인서터의 peek(놓을 수 있나 검사)은 레인 배열의
선두를, take(실제 집기)는 타일 중앙 최근접을 골랐다. 벨트가 정체돼 레인이 꽉 차면 둘이
갈린다 — 그리고 **기계 앞 벨트는 늘 정체돼 있다.** 못 놓는 아이템을 쥔 채 영원히 굳는다.

## 규칙으로 남길 것

- **경계 조건을 매개변수로 만들어라.** 회전·방향·재고 0·버퍼 만원처럼 값이 몇 개뿐인 축은
  전 조합을 도는 게이트를 하나 두는 편이 개별 케이스를 늘리는 것보다 싸다
  (`splitter.cellsMatchOccupancy` 는 4방향을 다 돈다).
- **"검사"와 "적용"을 같은 인자로 묶어라.** `free` 가 차감만 뜻하고 검사는 안 뜻했던 것이
  저장 결함의 뿌리다. 지금은 `canPlace(type,tx,ty,dir,restore)` 로 둘이 같은 스위치를 본다.
- **선택 규칙이 두 곳에 있으면 반드시 어긋난다.** peek/take 는 이제 `beltPick` 하나를 공유한다.
- **출고 전 독립 리뷰는 게이트의 대체재가 아니라 보완재다.** 게이트는 회귀를 막고,
  리뷰는 아직 생각해 본 적 없는 실패를 찾는다. 확정된 결함마다 게이트를 새로 달아
  둘을 잇는다(이번에 12건 추가).
